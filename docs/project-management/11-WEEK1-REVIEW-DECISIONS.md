### 발견한 표현 수정 필요 사항

**FIX-01 — PO 헤더 완료 조건: 반영 완료.** `../business/04-ERP-WORKFLOW.md` v0.3에서 모든 PO 품목의 `remainingQty == 0`을 기준으로 판정하도록 수정했다. 단위가 다른 품목 수량을 합산하지 않는다.

**FIX-02 — 인쇄 표현:** P0는 PO 상세에서 **브라우저 인쇄**, 독립 PDF 발행은 P1. 화면·API에서 이를 혼용하지 않는다.

**FIX-03 — 결제/실발주 구분:** 내부 PO 관리와 공급업체 연락처 **조회**만 P0. 결제 계획서 기반 PG 결제·실거래는 제외한다.

**FIX-04 — AI 화면 통합 범위:** 채팅과 파일 업로드가 하나의 화면에 있다는 뜻이지, A/B AI 로직을 하나의 거대한 Agent나 하나의 코드 파일로 합친다는 뜻이 아니다.

**FIX-05 — GR 이력:** P0는 GR 생성 후 `POSTED`, 취소/역거래는 P1. 성공한 GR 원장 이력을 직접 수정·삭제하는 P0 화면을 만들지 않는다.

### 4.1 PO 분할 발주 API/DB 설계에 추가할 검증

- `PurchaseOrderItem`은 원본 `RequisitionItem`을 참조하며 **1 PR item → N PO items**를 허용한다.
- 한 PO는 공급업체 한 곳, PR 품목별 유효 PO 발주 합계는 승인 수량 이하이다.
- PO 생성은 A 구매 서비스의 **별도 단일 DB 트랜잭션**이다. PR item 잠금 → 현재 발주 합계 재검증 → PO/Item 저장·멱등 결과 기록 순서로 설계한다.
- PR 품목에 대한 `UNIQUE(po.pr_id)` 같은 제약을 걸면 정상 분할 발주가 막히므로 금지한다.
- PO별 미입고 잔량과 PR별 미발주 잔량은 서로 다른 계산이며 화면에서도 분리한다.
- 테스트: 서로 다른 키 PO 60+40 성공, 60+60 경쟁 중 초과 요청 실패, 같은 키 중복은 기존 결과 반환.
