## 1.1 B 피드백 수용 — 2026-11-18 추가 (P0 범위)

**B가 주도 검토할 잔여 정책:** (1) 현재고가 양수인 창고·위치의 비활성화 차단 여부(차단 권고), (2) 동일 POItem·동일 저장위치 배분 중복 행 거부 여부(거부 권고), (3) DRAFT 입력 필드와 임시저장 접근 범위, (4) 확정 요청 재시도·멱등키 관리 및 오류 UX, (5) Document AI/ES 장애 재처리·매칭 정책.

**A/B 공동 결정:** (1) PRItem별 필요일/용도 추가 여부(공장 Plant 마스터는 P0 제외), (2) PO↔GR 서비스의 합산 DTO·잠금 순서, (3) POSTED 확정/버전 처리와 공통 오류 응답, (4) DB 마이그레이션 적용 전 계약 리뷰.

**중요:** 위 결정은 기존 X-08 '중복 금지', X-10 '같은 PO 품목은 한 GR에 한 행', GR '생성 즉시 POSTED'와 **양립하지 않는다**. 본 번들의 업무·DB·API·화면 정본은 위 최신 방향을 따른다. 실제 코드·팀 최종 승인은 별도이다.

## 2. 수용하지 않는 복잡도 (범위 제한의 이유)

- **다단계 결재·품목별 승인:** PR 전체 승인이라는 현재 도메인 결정과 충돌하며, 분할 발주와 무관한 추가 프로세스·권한 상태를 증가시킨다. 실무 가치가 없어서가 아니라 현재 핵심 정합성보다 우선순위가 낮다.
- **Kafka/RabbitMQ로 핵심 PO→GR→재고 분산:** 한 PostgreSQL 트랜잭션으로 보장해야 할 정합성에 불필요한 장애·재처리 경로를 추가한다. 비동기 작업 자체는 Document AI나 ES 색인에 필요해질 때 채택한다.
- **품목별 단위 환산·다중 통화·세금 복잡 모델:** 학습 가치가 있으나 이번 구매·입고 핵심 테스트를 끝낸 다음 별도 기능으로 고려한다.
- **관리자 무제한 대리수정·자기 승인 예외:** 업무 규칙을 훼손하면서 보안 복잡도를 증가시키므로 P0 미포함.

## 3. 기능 확장 후보: ERP 도메인 + 포트폴리오 가치에 따라 우선순위 부여

> **아래는 신규 제안이므로 현재 P0 확정 기능 40개에 자동 추가하지 않는다.** 핵심 P0 종단 간 시나리오가 실행·테스트된 후 채택 여부를 판단한다.

| 후보 | 우선 | 학습/업무 가치 | 구현 조건 및 고려사항 |
|---|---|---|---|
| GR 입고 취소/역거래 | P1 최우선 | 불변 원장·보정 트랜잭션·PO 누적입고 되돌리기·멱등 처리 | 기존 원장 UPDATE/DELETE 없이 반대 부호 이동 추가, 취소 중복 방지, 후속 입고와 동시 경합 처리 |
| 창고 내 위치 이동 / 창고 간 재고 이동 | P1 상 | 출고·입고 두 이동을 한 트랜잭션으로 처리, 원장 정합성·재고 부족 방지 | 이동 ID 기준 양쪽 원장을 연결, 동일 품목/위치 쌍 잠금 순서 고정 |
| PO 발주 취소/잔량 복원 | P1 중 | 분할 발주에서 PR 미발주 잔량 복원, 상태 전이 및 참조 정합성 | 입고된 PO 취소 정책은 별도 검토. 처음에는 미입고 PO만 취소하는 제한안부터 |
| 품목별 안전재고 기준 자동 부족 조회 | P1 중 | 재고 설정·조회 Tool 연계, 실제 활용 가능성 | 최소재고 설정 권한·평가 기준 확정 필요 |
| 품목별 부분 승인/다단계 결재 | P2 | 복잡 결재 설계 경험 | 권한 상태 폭증으로 현재 단계에서는 비용 대비 후순위 |

- `RBAC-MATRIX.md`: 복수 역할, 객체 소유권, 관리자 자기 승인 금지, 관리자 대리수정 비지원 정책 반영.

## 5. 반드시 통과해야 하는 구현 검증

1. 승인 PR 품목 100 → PO 60 + 40 성공; 동시 PO 60 + 60 중 하나 거부; 멱등 재시도에 중복 PO 없음.
2. PO 100 → GR 60 + 40 성공; 동시 GR 60 + 60에서 초과 입고 방지; 원장 실패 시 PO·GR·재고 전체 롤백.
3. **한 GR에 2개 품목, 동일 창고 내 각각 다른 저장위치로 입고** → 품목/위치별 현재고가 정확하고 원장 2건 생성.
4. 다른 창고 소속 또는 비활성 저장위치는 GR 저장 거부, 부분 성공 없음.
5. 사용자에 REQUESTER+APPROVER 복수 역할을 부여해도 본인 PR 승인 차단; 다른 사람의 DRAFT 수정 차단.
6. UI/Agent/Document AI가 모두 같은 PR DRAFT 서비스·버전 검증을 이용하며, 승인·PO·GR Tool 호출은 AI에서 금지.
7. 상태 충돌 후 최신 데이터 재조회; 동일 본문 재시도에는 동일 요청키, 수정 후 새 요청에는 새 요청키 사용.
8. `SCREEN-SPEC.md`의 실제 React 동작 검증, CI 및 마이그레이션 실행 확인은 별도 진행 — 문서 작성만으로 완료한 것으로 간주하지 않음.
