## 3. PO↔GR 단일 트랜잭션 계약 (A+B 핵심 합의)

### 3.1 애플리케이션 서비스 경계

1. B `GoodsReceiptApplicationService`가 트랜잭션을 시작한다.
2. 요청키 중복을 확인하며, 유일성 제약으로 경쟁 중복도 차단한다.
3. A `PurchaseOrderReceivingService`를 호출해 **동일 트랜잭션에서** PO 품목 행 잠금 후 최신 잔량을 검증·누적량 반영한다.
4. B가 `GoodsReceipt`, `GoodsReceiptItem`, `StockMovement`를 저장하고 `StockBalance`를 갱신한다.
5. PO 헤더의 `OPEN/PARTIALLY_RECEIVED/RECEIVED` 상태를 처리하고 트랜잭션을 커밋한다.
6. 어느 한 단계라도 실패하면 **전부 롤백**한다.

**금지:** B가 PO Repository를 직접 갱신, Rust AI 서비스가 ERP DB 직접 쓰기, DB 트랜잭션 안에서 외부 HTTP 호출로 원자적 커밋을 시도하는 것.

**별도 PR→PO 분할 발주 트랜잭션(A 소유):** 구매 담당자가 PO 생성 명령을 제출하면 요청키 중복을 검증하고, **PR 헤더/품목(품목 ID 오름차순)을 잠근 후** 현재 유효 발주 합계를 재계산한다. 새 PO 헤더(공급업체 1곳)와 PO Item을 같은 트랜잭션에서 생성한다. PR 전체에 PO 1건만 허용하는 UNIQUE 제약을 두지 않는다. PO 생성과 GR 처리는 서로 다른 트랜잭션이고, GR은 개별 PO를 참조한다.

### 3.2 동시성·멱등성 설계안 (방법은 합의 필요)

- **GR 동시성:** PO 품목 레코드를 비관적 잠금 등으로 직렬화하고 잠금 뒤 남은 수량을 다시 계산한다. 여러 품목 입고 시 품목 ID 오름차순 등 잠금 순서를 고정한다.
- **중복:** `requestId`(멱등성 키)를 요청별로 부여하고 DB 유니크 제약을 적용한다. 서버 인스턴스가 둘이어도 중복 입고를 막아야 한다.
- **재시도:** 같은 키·같은 내용이면 기존 처리 결과를 반환(권장), 같은 키·다른 내용이면 충돌 처리. 실패한 요청의 재시도 정책은 API 계약에서 정한다.
- **재고 행 생성 경쟁:** `(materialId, warehouseId, storageLocationId)`에 유니크 제약을 두고 새 행 생성/기존 행 갱신의 경합을 제어한다.
- **불변 이력:** 성공한 `StockMovement`는 수정/삭제하지 않는다. 취소는 차후 역이동 기록으로 처리한다(P1).
- **검증:** 잠금 방법을 정한 뒤 통합 테스트에서 동시 입고 수량이 초과하지 않는지 실제 PostgreSQL로 확인한다. DB만 Mock한 테스트로 동시성 검증 완료를 주장하지 않는다.

## 5. P0 제외·추후 확장

- **P1:** 이미 게시한 GR 취소·101의 역이동에 해당하는 처리, 재고 역거래, 발주서 정식 PDF·인쇄 사용성 고도화, 인덱스 재색인 고도화.
- **P2/이번 일정 제외:** 다단계 결재, 송장 대조, 가상 지급, OCR, BOM/간소화 MRP.
- **완전 제외:** 실제 발주 전송·PG/대리결제·실제 자금 이동, MES·설비 제어, 실제 SAP 서버 연동.

## 6. A가 선택한 방향과 후속 상세 결정 (중요도 순)

| 우선 | 의사결정 | 권장 초안 | 책임 |
|---|---|---|---|
| 1 | **PR↔PO 관계** | **확정 방향: 1 PR → N PO; 각 PO 공급업체 1곳·PR 품목 수량 분할, 승인 수량 초과 금지** | A+B |
| 2 | **승인 단위·반려 재작업** | **확정 방향: PR 헤더 전체 일괄 승인/반려**, `REJECTED → DRAFT`; 품목별 승인 제외 | A+B |
| 3 | **PO↔GR 서비스 DTO·호출 경계** | A PO 수량 서비스, B GR 트랜잭션, 동일 DB | A+B |
| 4 | **단위·수량 정밀도** | 품목별 기준 UOM 하나로 저장, 수량 `NUMERIC`, P0 단위 변환 없음 | A+B |
| 5 | **업무 권한** | REQUESTER/APPROVER/PURCHASER/WAREHOUSE, 상세 접근은 기능별 검증 | B 공통 + A/B |
| 6 | **GR 멱등성** | 클라이언트 요청키+DB 유니크, 동일 키/같은 페이로드 기존 결과 | B 중심 + A 리뷰 |
| 7 | **잠금·StockBalance 생성 정책** | PO 품목 먼저 잠금, 재고 행은 유니크+경쟁 제어 | A+B |
| 8 | **취소/완료 정책** | P0 자동 완납만 지원, PO 취소·입고 취소는 제외 | A+B |

이 정책을 B와 검토한 뒤 3일 차 `../planning/FUNCTIONAL-SPEC.md`의 참조 조건을 확정하고 `../database/DB-SPEC.md`, `API-CONTRACT`에 ID·컬럼·API를 반영한다. **이 문서만으로 ERD와 API가 확정되었다고 표현하지 않는다.**

### 이번 개정에서 바뀐 내용만 요약

- **유지:** 승인 전 PO 금지, 반려 재작업, 부분 입고, 초과/중복/동시 입고 차단, GR 단일 DB 트랜잭션.
- **보완:** 품목별 `PR Item → PO Item → GR Item` 참조, 저장위치 소속 검증, 기준단위 일치, 공급업체 연락처의 조회용 성격.
- **D-01~02 방향 수용:** 1 PR→N PO, PR 헤더 일괄 승인. D-03~11 권장 방향은 A가 수용하였으나 NUMERIC 정밀도, 기술 PoC, 서비스 간 신원 위임·DB/REST 구체 구현은 남아 있다. EDMX만으로 이를 확정하지 않는다.
