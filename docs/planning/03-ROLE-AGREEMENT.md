# 차곡ERP — 2인 역할 분담·책임·협업 계약

> **문서 버전:** v0.3 · 2026-11-17  
> **기준:** [통합 기획서 v3.3](차곡ERP_통합기획서_v3.3.md) · [PRD](01-PRD.md) · [MVP 범위표](02-MVP-SCOPE.md)  
> **구성:** 개발자 A(본인), 개발자 B(친구) / 2명 / 최대 20주  
> **상태:** 최근 대화에서 확정한 책임을 반영한 팀 공유 문서. 서명 및 개별 세부 기술 선택은 아직 별도 확인 필요.

## 1. 분담의 원칙

1. **ERP 개발과 AI 개발은 동등한 핵심 축**이다. A/B 모두 실질적인 ERP 도메인과 AI 구현 성과를 책임진다.
2. ERP는 Java·Spring Boot 중심의 **모듈형 모놀리스**이며, 기능별 업무 규칙·Repository·영속화는 해당 도메인 소유자가 담당한다.
3. A/B가 서로의 DB 테이블을 임의로 변경하지 않는다. 공개된 서비스·API 계약 및 공동 ERD 리뷰를 따른다.
4. **공통 디자인은 A**, **공통 사용자·인증·역할/권한 인프라는 B**가 맡는다. 각 도메인 내부 업무 권한 검증은 각 소유자가 수행한다.
5. **CI/CD·배포 인프라·공통 로깅/모니터링·PostgreSQL 공통 운영**은 A와 B가 **함께 작업한다**. 담당 미정으로 남기지 않는다.
6. 통합 AI Assistant는 하나의 화면이지만, Agent와 문서 파싱·매칭 서비스의 코드 책임은 분리한다.
7. DB를 '50:50'으로 개발한다는 것은 테이블 수를 기계적으로 나누지 않고 **도메인별 모델·트랜잭션 책임을 균형 있게 가진다**는 뜻이다.

## 3. 개발자 A — 상세 범위

### 3.1 ERP 구매·기준정보

- Material: 품목 코드·명칭·규격·단위·상태, 중복 코드 차단.
- Supplier: 공급업체 코드·명칭·전화·이메일·활성 상태 및 PO 참조.
- PR: DRAFT 저장/수정/제출, 승인·반려·수정 버전 및 문서 이력.
- PO: **실제 전송 없는 내부 발주 기록**. 승인된 PR 1건에서 **여러 PO**를 생성할 수 있으며 PO당 공급업체 1곳. PR 품목별 승인 수량을 여러 PO에 나누되 유효 발주 합계가 이를 넘지 않도록 락·멱등성 검증. 상세 조회·브라우저 인쇄.
- PO→GR 공개 서비스: 입고 가능 상태·잔여 수량 검증, 누적 입고량 반영, 원발주 수량 보존, 잠금·실패 응답 계약.
- 실제 PG·실거래·대리결제 기능은 개발하지 않음.

- 품목별 개별 승인 없이 PR 전체 일괄 승인·반려. 승인된 PR의 `RequisitionItem`은 여러 `PurchaseOrderItem`에서 참조 가능하며 발주 가능 잔량을 계산한다.

### 3.2 대화형 Agent 및 구매 규정 RAG

- 자연어 요청 의도, 문맥·후속 참조, 재질문.
- 품목·재고·공급업체·이전 구매 내역 Tool의 실행 흐름·오류 처리.
- RAG의 문서 색인·검색·출처·시행일 확인·답변 유보.
- 공통 PR DRAFT 생성·수정, `draftId`/버전·항목 ID 검증, 멱등성.
- Agent 권한·업무 상태 위반 처리, 허용 Tool 목록 관리, 규정 근거·작업 성공·지연·비용 평가.
- **승인·PO 확정·GR·재고·결제 자동 실행 Tool은 P0에 제공하지 않음.**

### 3.3 디자인·화면

- 공통 메뉴·사이드바·헤더·업무 테이블·폼·모달·상태·오류 디자인.
- Google AI Studio 등으로 대표 화면을 빠르게 시각화하되, Mock 데이터·임시 서버 코드는 실제 ERP 계약과 구분.
- 품목·공급업체·PR·승인·PO 및 **통합 Assistant의 채팅 Shell** 구현.
- B의 문서 검토 패널과 통합 화면에서 함께 동작하도록 연결.
- **A가 모든 React 화면을 대신 구현하는 것은 아님.** B는 자신의 화면을 구현한다.

### 3.4 데이터·테스트

- 구매 도메인 Entity·Repository·DB 마이그레이션 및 정합성 테스트.
- Agent 대화/실행 이력에 필요한 데이터·평가 테스트.

## 4. 개발자 B — 상세 범위

### 4.1 입고·재고 ERP

- 창고·저장위치 기준정보.
- GR 문서 및 부분 입고 처리, StockMovement·StockBalance 조회·갱신.
- **GR 트랜잭션 오케스트레이션 소유**: A의 PO 수량 서비스를 호출하여 같은 PostgreSQL 트랜잭션 안에서 GR·원장·현재고 반영.
- 동일 요청 중복 처리·동시 경쟁·전체 롤백 테스트.
- P1로 입고 취소·역거래 상세 고도화.

### 4.2 Document AI·품목 검색/매칭

- Excel·텍스트 PDF 파싱, 추출 필드 구조화·검증.
- 품목 코드 일치·정규화·약어·유사어 기반 **Rule-Based 우선 처리**.
- Elasticsearch BM25 검색/후보 선정, 규격·단위 불일치 검증.
- 필요 시 LLM 후보 비교 및 명확하지 않은 결과의 사용자 확인 요청.
- 통합 Assistant 내 파일 첨부·추출 결과·후보 비교·수량 수정 화면 구성.
- 사용자 확인된 값으로 A의 PR DRAFT 서비스 호출.
- 필드 추출·검색 Top-1·Recall@5·오확정률·지연·비용 평가.
- Vector/Hybrid Search 심화·재색인 개선은 P1.

### 4.3 공통 인증·사용자·권한 인프라

- 사용자와 역할/권한 관련 공통 데이터 모델 및 구현.
- 인증·로그인·로그아웃, Spring Security 공통 구성, 인증·인가 오류 계약.
- 공통 접근 제어와 사용자 식별 문맥 전달, ERP ↔ AI 서비스 간 신뢰할 수 있는 인증 정보 전달 방안 설계.
- A의 디자인 시스템을 사용하는 로그인 화면의 기능 연동.
- 각 도메인별 업무 권한 규칙은 해당 소유자가 직접 검증할 수 있도록 공통 기반 제공.
- **인증 방식(JWT/세션·쿠키 등)은 맡는 사람이 일방적으로 확정하지 않고 A와 계약 합의**.

### 4.4 데이터·테스트

- 창고·입고·재고, 문서 결과·매칭 검토, 사용자·역할 데이터 모델 및 관련 DB/서비스 테스트.

## 5. 공통 작업 — 이미 A+B로 확정

| 공통 영역 | 공동 수행할 작업 | 완료·검증 조건 |
|---|---|---|
| **CI/CD** | 빌드·테스트·PR 검사·배포 파이프라인 규칙 | PR 실패 조건, 빌드·테스트 실행 결과 검토 |
| **배포 인프라** | 서비스 구성·환경변수·도메인/통신·서버/컨테이너 실행·장애 재시작 | 실제 통합 배포에서 두 AI 경로·ERP 재현 |
| **공통 로깅·모니터링** | 로그 포맷, 오류·트랜잭션·AI 호출·리소스 관측 | 장애 원인 확인, 비밀정보 마스킹, 비용 확인 |
| **PostgreSQL 공통 운영** | 공유 개발 DB 실행·백업·복원·마이그레이션 규칙·권한 관리 | 환경 재구성·백업/복구 절차 문서 및 실행 검증 |

**협업 방식:** 공통 과제는 회의에서 작은 이슈로 나누고 각 이슈의 구현 담당과 리뷰 담당을 정한다. 전체 책임은 두 사람 모두가 가진다. 어느 한 사람이 '최종 운영 책임'을 떠안는 것으로 해석하지 않는다.

추가로 **전체 ERD·공통 API·공통 권한 매트릭스·종단 간 통합 테스트**는 두 사람이 함께 검토한다.

## 6. 핵심 모듈 계약 및 데이터 소유권

### 6.1 A의 PO ↔ B의 GR

- **A 소유:** PO 상태·발주 품목·원발주 수량·누적 입고량·잔량, 입고 가능 조건을 검증하는 서비스.
- **B 소유:** GR 생성·수량 기록, StockMovement/StockBalance, 입고 트랜잭션의 호출 순서 및 처리 결과.
- B는 A의 PO Repository를 직접 갱신하지 않고 공개 서비스 계약을 사용한다.
- PO·GR·재고는 **하나의 PostgreSQL 로컬 트랜잭션**에서 성공/실패해야 한다. 네트워크를 경유해 트랜잭션 원자성을 흉내 내지 않는다.
- PO 잠금 순서, DB 유일성 제약 및 멱등 요청키, 상태·오류 코드, 반영/롤백 테스트를 공동 설계한다.

- **PR→PO 분할 발주 계약(A):** 동일 PR의 여러 PO는 정상 업무다. 중복 차단은 PR 전체에 `UNIQUE`를 걸지 않고 **PR 품목별 발주 가능 잔량 + PO 생성 요청키**로 판단한다. 같은 PR 품목에 경쟁 PO 생성 시 PR 품목을 정해진 순서로 잠그고 유효 발주량 합계를 다시 검증한다.

### 6.2 A의 Material ↔ B의 검색 인덱스

- **PostgreSQL Material이 단일 원본**이다.
- B는 Elasticsearch 색인·갱신·재색인·후보 검색을 소유한다.
- 인덱스 지연·누락이 있더라도 PR 저장 시 A의 ERP 서비스가 원본 품목 ID·단위를 재검증한다.
- 별도의 색인 이벤트·재시도 구조는 실제 운영 요구에 따라 선택한다.

### 6.3 A의 PR ↔ A의 Agent/B의 Document AI

- A의 PR DRAFT 서비스만 최종 업무 검증과 DB 저장을 수행한다.
- A의 Agent 및 B의 문서 모듈은 공통 `materialId`·수량·단위·요청 사용자 문맥·버전 계약을 사용한다.
- B는 추출/매칭에 실패한 품목을 임의 확정하지 않고 사용자에게 검토를 요청한다.
- A의 Agent는 `draftId`·`version`과 화면 표시 품목→실제 항목 ID를 사용한다.

### 6.4 B의 인증 ↔ A/B 도메인 ↔ AI

- B는 사용자 인증·역할 기반을 구현한다.
- A/B는 자기 도메인에서 **문서 소유권·승인/입고 가능 상태와 세부 업무 권한**을 검증한다.
- AI 서비스는 신뢰되지 않는 클라이언트 `userId`만으로 권한을 얻을 수 없다.
- Rust AI 서비스가 채택되더라도 ERP DB를 직접 쓰지 않고 인증된 ERP API/서비스 계약을 사용한다.

### 6.5 UI 통합 계약

- **A:** 공통 디자인 시스템·메뉴·AI Assistant Shell·채팅/근거/PR 응답.
- **B:** 파일 첨부·추출 결과 표·매칭 후보·품목 수정/확정과 로그인 기능 연동.
- 사용자가 보기에는 **하나의 Assistant**이며 중복 Agent나 두 번째 별도 채팅 화면을 필수로 요구하지 않는다.

## 8. 기술 결정 사항과 공동 의사결정

| 항목 | 현 상태 | 누가 결정하는가 |
|---|---|---|
| Java/Spring Boot 상세 버전 | 미확정 | A+B |
| Rust AI 서비스·Rig 채택 | PoC 필요 | A+B |
| LLM·Embedding 모델 및 비용 | 미확정 | A+B |
| 인증 방식 | **Spring Security 세션·HttpOnly 쿠키 우선**, CSRF·Rust 신원 위임 상세 미확정 | B 설계안 → A+B 검토 |
| 세부 권한 매트릭스 | 미확정 | 각 도메인 + B 공동 |
| GR 잠금·멱등 원칙 | **PO 잠금 + 요청키 UNIQUE + 단일 트랜잭션 방향 수용**; 상세 구현·취소는 미확정 | A+B |
| PostgreSQL 마이그레이션 도구 | 미확정 | A+B |
| Elasticsearch 색인 동기화 | **DB 커밋 이후 반영·실패 재처리 방향 수용**, 상세 구현 미확정 | A+B |
| 배포 플랫폼·환경·비용 | 미확정 | A+B |
| 디자인 세부 스타일 | A 주관, 팀 검토 | A 제안 → A+B 검토 |

**담당자 지정은 기술 선택 확정과 다르다.** 미확정 결정을 이미 구현된 사실로 표현하지 않는다.

## 9. 완료·검증·변경 관리

- 각자 기능의 명세·API·DB 코드·화면·테스트를 소유한다. 공통 기능은 이슈 단위로 구현자를 나눈다.
- API/DB/권한 계약 변경 시 다른 담당자가 영향을 받는지 먼저 검토하고 PR에 기록한다.
- 브랜치·PR·리뷰·커밋·코드 스타일은 제공된 `../../CONTRIBUTING.md`, PR 템플릿, `CLAUDE.md`, `../../.editorconfig`, Java 스타일 문서를 따른다.
- AI 생성 코드도 정상·실패·동시성 검증을 거쳐 병합한다.
- 최소 종단 간 테스트는 **수동 PR→내부 PO→부분 GR→재고**와 **Assistant 대화→PR**, **문서 첨부→매칭→PR** 세 경로다.
- 결제·송장·다단계 결재·MES를 개발 범위에 다시 넣으려면 별도 범위 변경 합의가 필요하다.
