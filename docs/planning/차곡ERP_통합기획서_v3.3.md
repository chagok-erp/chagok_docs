## 1. 프로젝트 정의

차곡ERP는 **SAP S/4HANA의 공개 구매·재고 업무 프로세스와 공식 API 명세를 참고**해 구매·재고 ERP를 **직접 구현**하고, 자연어 업무 Assistant와 비정형 구매문서 처리 AI를 연결하는 서비스다. 자체 ERP의 업무 규칙·데이터 모델·트랜잭션은 Spring Boot와 PostgreSQL에서 관리한다.

**ERP와 AI는 동등한 핵심 영역**이다. AI가 없어도 PR(구매요청) → 승인 → PO(내부 구매발주) → GR(입고) → 재고 반영이 작동해야 하며, AI는 허용된 업무 조회와 **PR 초안 생성·수정**을 통해 이를 지원한다.

실제 SAP 서버 및 ABAP을 사용하지 않는다. SAP 문서의 설계 참고와 실제 SAP 제품 개발·운영 경험은 구분한다.

### 해결할 문제

1. 구매요청부터 입고·재고까지 분리된 정보를 연결하지 않으면 문서 상태와 입고 가능 수량을 관리하기 어렵다.
2. Excel·텍스트 PDF 구매문서의 품목명·규격·수량을 ERP 기준정보에 맞춰 입력하는 수작업이 반복된다.
3. 구매 담당자는 재고·이전 구매 내역·공급업체·구매 규정을 여러 화면에서 확인한다.
4. 중복·동시 요청과 AI의 잘못된 추정이 실제 ERP 데이터를 변경하지 못하도록 통제해야 한다.

### 참고 사례의 반영 범위

기존에 검토한 **김동년 포트폴리오의 비정형 주문발주 데이터 자동화 사례**에서 `문서 파싱 → 구조화 → 품목 매칭 → 사용자 검토 → ERP 기록` 흐름과 `Rule-Based 우선, 불확실한 경우 AI 보조` 원칙을 참고한다. 해당 사례의 성능 수치, 유사어 사전 규모, 워크플로 노드 수를 차곡ERP의 구현 실적이나 목표 수치로 가져오지는 않는다. 업종과 데이터 특성이 다르므로 제조 부품에 맞게 설계·측정한다.

## 2. 대상 사용자 및 업무 권한

| 역할 | 업무 |
|---|---|
| 요청자 | 품목 조회, PR 초안 생성·수정·제출, 상태 조회 |
| 구매 담당자 | 승인된 PR을 내부 PO로 전환, 공급업체·발주 금액 관리 |
| 승인자 | 단일 단계 승인·반려 및 이력 확인 |
| 창고 담당자 | PO를 참조한 수동 GR·부분 입고, 재고·원장 조회 |
| 관리자 | 사용자·역할, 기준정보 관리 |

권한은 서버에서 **역할 + 문서 소유권 + 업무 상태**를 함께 검증한다. AI 역시 로그인 사용자에게 허용된 작업만 실행한다. 세부 권한 매트릭스는 `ERP-SPEC.md`에서 확정한다.

## 3. ERP 핵심 프로세스와 발주·결제 범위

```text
품목·공급업체·창고 기준정보
          ↓
구매요청 PR (수동 / 대화형 AI / 문서 AI → 공통 초안 서비스)
          ↓
제출 → PR 전체 일괄 승인 / 반려(수정 후 재제출)
          ↓
승인된 PR 품목별 발주 가능 잔량 확인
          ↓
내부 PO 1개 이상 생성(분할 발주)
(PO마다 공급업체 1곳, 품목별 발주 수량·단가·총액 관리)
(같은 PR 품목을 여러 PO로 나눌 수 있으나 총 발주량은 PR 승인 수량 이내)
(공급업체 연락처 확인·발주 내역 인쇄)
          ↓
[실제 공급업체 주문 전송·실구매·결제 없음]
          ↓
가상 납품 상황을 가정한 창고 담당자의 수동 입고 GR
(부분 입고 가능, 초과·중복 입고 금지)
          ↓
PO 누적 입고량 + GR 문서 + 재고 원장 + 현재고 일관 반영
```

**내부 PO와 실제 거래는 다르다.** PO는 입고의 기준인 ERP 내부 발주 기록으로 **P0 유지**한다. 실거래처 발주 전송, PG 테스트·실결제, 대리결제·자금 이체는 **P0 및 이번 프로젝트 범위에서 제외**한다. PO 금액은 **예상 발주 금액**이지 지급 완료 금액이 아니다. 공급업체 전화번호·이메일은 정보 확인용이다. 발주서 상세 조회·브라우저 인쇄는 P0, 정식 PDF 생성은 P1 후보로 둔다.

대금 지급을 확장한다면 입고·송장 검증을 거친 **모의 지급 상태 관리**를 장기 P2 후보로 검토한다. 단, 이번 5개월 내 구현을 약속하지 않으며, 실제 돈이 이동하는 결제와 구분한다.

### 핵심 업무 규칙

- 미승인 PR로 PO를 생성할 수 없다. 요청·승인·발주·입고의 상태 변경과 처리 이력을 기록한다.

- **D-01 확정 방향:** 승인된 PR 1개에서 공급업체별·수량별로 여러 PO를 발행할 수 있다. PO 하나는 공급업체 한 곳을 참조한다. 각 PO 품목은 원본 `RequisitionItem`을 참조한다.
- **분할 발주 수량 불변식:** PR 품목별 `Σ(유효 PO 품목 발주량) <= PR 승인 수량`을 유지한다. 발주 가능 잔량은 승인 수량에서 유효 PO에 이미 발주한 수량을 뺀 값이다. 동일 PR 품목의 경쟁 PO 생성은 DB 잠금/멱등 키로 검증한다.
- **D-02 확정 방향:** 승인·반려는 PR 헤더 전체에 한 번 적용한다. 품목별 선택 승인이나 수량 조정 승인은 이번 P0 범위에 없다.
- PO의 **원발주 수량은 유지**하고, 누적 입고량을 별도로 관리한다.
- 100개 발주 후 60개, 40개를 나누어 입고할 수 있으며, 잔량을 넘는 입고는 거절한다.
- GR 생성, PO 누적 입고량, StockMovement, StockBalance는 **같은 PostgreSQL 트랜잭션**에서 모두 반영되거나 롤백한다.
- 동시 입고에는 일관된 잠금 순서 및 DB 제약·멱등성 검증을 적용한다.
- 입고 취소·역거래의 상세 고도화는 P1이다. 초기 P0는 부분 입고·정합성에 집중한다.

## 4. AI — 단일 사용자 경험, 두 내부 처리 영역

사용자는 **하나의 AI Assistant 화면**에서 채팅과 파일 첨부를 사용한다. 내부 구현과 책임은 다음처럼 나눈다.

```text
                  통합 AI Assistant UI
               (채팅 + 파일 첨부 + 결과 검토)
                      /          \
        대화·ERP Agent(A)      Document AI·검색(B)
        - 대화 문맥            - Excel/텍스트 PDF 파싱
        - ERP 조회 Tool        - 구조화·필드 검증
        - 구매 규정 RAG        - 품목 코드/규칙 기반 매칭
        - 재질문·초안 수정     - Elasticsearch BM25 후보
                               - 필요 시 LLM 판단·재검증
                      \          /
                 사용자의 품목·수량 검토
                          ↓
            Spring Boot 공통 PR 초안 서비스(A 소유)
                          ↓
                       PostgreSQL
```

### 4.1 대화형 업무 Agent (A)

- 자연어 의도·대화 문맥·후속 참조 처리(예: “두 번째 품목 제외”).
- 품목·재고·공급업체·이전 구매내역 조회 Tool과 구매 규정 RAG.
- 구매 규정의 출처·시행일 표시, 근거 부족 시 유보·재질문.
- **PR DRAFT 생성·수정**: 저장된 `draftId`, `version`, 표시 항목↔실제 품목 ID 매핑 사용.
- 위험 작업 제한: AI가 승인, PO 최종 확정, GR, 현재고 변경, 결제를 직접 실행하지 않음.
- 오류·권한 실패·동시 수정 충돌을 숨기지 않으며 실행 로그·지연·비용을 측정.

### 4.2 문서 처리 AI·품목 매칭 (B)

- 합의한 샘플 범위의 Excel 및 **텍스트 기반 PDF** 파싱. 정형 데이터는 일반 파서를 먼저 사용.
- 품목명, 규격, 단위, 수량의 구조화·형식 검증, 누락·불일치 표시.
- **1차:** 품목 코드, 문자열 정규화, 제조 부품 특화 동의어·약어 및 검증 규칙.
- **2차:** Elasticsearch BM25/키워드 검색으로 후보 선정.
- **3차:** 후보가 모호한 경우에만 LLM 비교·판단, 규격·단위 재검증.
- **최종:** 사용자가 후보와 수량을 수정·확정한 뒤 A의 공통 PR 초안 서비스로 저장.
- P1: Vector/Hybrid Search 및 정량 비교 확대, 재색인·매칭 실패 복구 고도화.
- 이미지·스캔 PDF OCR과 모든 양식 지원은 P0에서 제외.

Document AI는 Agent 내부의 거대한 다중 Agent 체인으로 강제하지 않는다. 통합 Assistant 화면의 파일 처리 기능으로 연동하되, 독립 테스트 가능한 모듈을 유지한다.

## 5. MVP 우선순위

### P0 — 반드시 완료

| 영역 | 필수 범위 |
|---|---|
| ERP 기준정보 | 품목·공급업체(연락처), 창고·저장위치 |
| 구매 | PR 초안·제출·헤더 전체 승인·반려·**분할 PO 생성/발주 잔량 관리**·조회·발주 내역 인쇄 |
| 입고·재고 | 수동·부분 GR, PO 잔량 검증, 중복·초과 입고 차단, 재고 원장·현재고 |
| 대화형 AI | 조회 Tool, 기본 RAG, 문맥·재질문, PR 초안 생성·수정, 사용자 권한과 실패 처리 |
| 문서 AI | Excel·텍스트 PDF 파싱, 구조화, 규칙/검색/필요 시 LLM 매칭, 사용자 검토, PR 초안 생성 |
| 공통 | 통합 Assistant UI, 인증·인가, 반응형 웹 기본, 기본 평가·자동화 테스트·배포 |

### P1 — P0 안정화 후

입고 취소·역거래 상세 고도화, Agent 재시도·문맥 고도화, Vector/Hybrid Search 평가 확대, 문서 품목 재매칭·재색인, AI 운영 평가 화면, 예상 발주 금액 집계(실제 지급액과 구분), 정식 PO PDF 출력, SAP 공식 Sandbox 검증, 반응형 개선.

### P2 — 이번 일정의 완료 약속이 없는 장기 확장

BOM·간소화 자재 소요량 계산 및 부족 품목 PR 연계, 다단계 결재, 송장 대조 및 **모의 지급 상태 기록**, OCR, Multi-Agent, 모바일 앱/PWA, 실제 SAP 연동, 생산·회계 등 인접 모듈.

### 이번 5개월 범위 제외

실제 공급업체 발주 전송, **실구매·실결제·대리결제·PG 결제 연동**, 실자금 이체·정산, 다단계 결재, 송장 검증의 본격 구현, MES 전체, 작업지시·생산실적·설비 제어/모니터링, SAP 서버 운영·ABAP 구현, 인사·급여, Kubernetes 필수 도입.

**P2는 구현 보장 항목이 아니다.** 다단계 결재·송장 검증은 이번 범위에서 제외하면서 미래 후보로만 남긴다. BOM·간소화 MRP 역시 MES 구현이 아닌 ERP 생산 연계 확장안이다.

상세 기능별 완료 기준과 담당자는 [MVP 기능 범위표](02-MVP-SCOPE.md)를 따른다.

## 6. 역할 분담 — 최종 반영

| 영역 | 개발자 A (본인) | 개발자 B (친구) |
|---|---|---|
| ERP | Material·Supplier, PR, 헤더 전체 승인·반려, **PR→여러 PO 분할 발주·수량 배분** | Warehouse·StorageLocation, GR, StockMovement·StockBalance |
| PO↔GR 연결 | PO 입고 가능 상태·누적 수량 서비스 | GR 조정·PO 서비스 호출·재고 원자적 처리 |
| AI | 대화형 Agent, Tool Calling, 구매 규정 RAG, PR 초안 생성·수정 | 문서 파싱·구조화, 품목 검색·정규화·매칭, LLM Fallback |
| UI 구현 | 구매·Agent 화면 | 입고·재고·문서 검토 화면 |
| 공통 디자인 | **A: 공통 UI/UX 디자인·디자인 시스템·AI Studio 프로토타입** | A의 공통 디자인 기준으로 담당 화면 구현 |
| 공통 인증 | 업무별 구매 권한 세부 검증 | **B: 공통 인증·사용자·역할 인프라 및 로그인 연동** |
| DB | 구매·Agent 도메인 모델과 정합성 | 재고·Document AI·인증 도메인 모델과 정합성 |
| 공동 작업 | **CI/CD, 배포 인프라, 공통 로깅·모니터링, PostgreSQL 공통 운영 환경·백업/복구** | **동일 — 공동 책임** |

**공동 운영은 '주담당 미정'이 아니라 '두 사람 공동'으로 결정했다.** 구체적인 작업 단위는 이슈·PR로 나눠 맡되, 설정과 결과는 모두 리뷰한다. 전체 ERD·API 계약·통합 테스트도 공동 검토한다.

## 7. 기술 구조 및 검토 대상

| 계층 | 설계 방향 | 확정 여부 |
|---|---|---|
| Web | React·TypeScript, PC 우선 반응형 | 방향 합의 |
| ERP | Java·Spring Boot, 모듈형 모놀리스 | 방향 합의 |
| ERP 원본 DB | PostgreSQL | 방향 합의 |
| 검색 인덱스 | Elasticsearch; 원본 품목은 PostgreSQL | 방향 합의 |
| AI Backend | Rust·Axum·Rig 후보, Spring AI 대체 검토 | **PoC 후 확정** |
| LLM·Embedding | 평가·예산·기능 적합성 비교 | 미확정 |
| 로컬/배포 | 단순 실행부터 시작, Docker Compose 기본 후보; Aspire 선택 검토 | 세부 미확정 |
| 추가 도구 | Redis·Spring Batch·MCP·다중 Agent 필요성에 따라 검토 | 필수 아님 |

Rust AI 서비스를 채택하는 경우 ERP 도메인 데이터는 해당 서비스가 직접 수정하지 않는다. 사용자 인증·권한 정보를 신뢰할 수 있는 방식으로 Spring Boot에 전달하며, **ERP 서버가 항상 최종 권한·업무 상태를 검증**한다.

### 대표 데이터 모델(초안)

- A: `Material`, `Supplier`, `PurchaseRequisition`, `RequisitionItem`, `ApprovalHistory`, `PurchaseOrder`, `PurchaseOrderItem`, Agent 대화·실행 이력.
- B: `Warehouse`, `StorageLocation`, `GoodsReceipt`, `GoodsReceiptItem`, `StockMovement`, `StockBalance`, 문서 처리·매칭 검토 이력, **`User`·`Role` 관련 공통 인증 데이터**.
- 전체 ERD·FK·공통 식별자·수량·단위·마이그레이션은 두 사람이 공동 검토.

## 8. 반드시 먼저 합의할 모듈 계약

**PR ↔ PO 분할 발주**: A는 PR 품목별 승인 수량과 이미 발주한 수량을 원자적으로 확인해, 하나의 PR 품목을 여러 PO로 나누어도 초과 발주가 발생하지 않게 한다. 한 PO는 공급업체 1곳을 참조한다. PR 품목 ID 참조·발주 가능 잔량·멱등성·동시성은 A의 구매 서비스와 DB 명세에 포함한다.

**PO ↔ GR**: A는 PO 품목의 잔여 수량·상태·잠금·누적 수량 갱신 서비스를 제공한다. B는 입고 트랜잭션을 조정하면서 A의 서비스를 호출하고 GR·StockMovement·StockBalance를 처리한다. PO 원발주 수량은 변경하지 않는다. 잠금 순서, 유일성 제약, 취소 정책을 공동 설계한다.

**Material ↔ Elasticsearch**: A의 PostgreSQL 품목이 원본, B의 Elasticsearch가 검색용 인덱스다. 색인 누락·지연과 재색인 전략을 정의하고, PR 저장 전 ERP 원본 품목·단위를 재검증한다.

**Agent / Document AI ↔ PR DRAFT**: A의 단일 PR 서비스가 생성·수정·검증·영속화를 책임진다. B는 사용자 확인을 끝낸 확정 품목 ID·수량·단위를 동일 계약으로 전달한다. Agent는 `draftId`·버전을 사용한다.

**인증 ↔ AI ↔ 도메인**: B가 인증·권한 기반을 제공하고, A와 B가 각각 자신의 ERP 업무에서 세부 권한을 검증한다. AI Tool은 역할/소유권을 우회하지 못한다.

## 9. 화면 및 UX 계획

A가 AI Studio로 공통 디자인을 시도하고, 두 사람이 대표 화면으로 사용 흐름을 검토한다. 디자인 원칙은 **업무 효율 중심, 테이블·폼·상태·오류 안내의 일관성**이다.

## 12. 품질·평가 및 완료 기준

- **ERP:** 승인 수량 100개인 PR 품목에 PO 60개 + 40개 분할 발주 가능(추가 1개 거부); 각각 PO에서 정상 입고 가능. 100개 PO에 60·40개 입고; 초과·동시·중복 입고 차단; 오류 시 PO·GR·재고 전체 롤백; 승인되지 않은 PO 전환 차단; 권한 검증.
- **Agent:** 조회·RAG 근거·초안 생성/후속 수정·재질문·권한 실패를 테스트. Tool 선택, 업무 완료, 응답 지연·비용 기록.
- **Document AI:** 지정 Excel·텍스트 PDF에서 추출·매칭·사용자 확인 후 PR 생성. 필드 정확도, Top-1, Recall@5, 오류·오확정률·비용 측정.
- **운영:** 공통 CI/CD, 로그·모니터링, PostgreSQL 백업·복구 절차, 한 환경에서 핵심 흐름의 반복 시연.
- 실측하지 않은 비용 절감률·정확도·처리 속도를 주장하지 않는다.

## 13. 결정 사항과 미확정 사항

### 이번 개정에서 반영한 결정

1. 채팅·파일 업로드는 **하나의 AI Assistant UX**, 내부 개발 책임은 A/B 유지.
2. Document AI는 **규칙·품목 코드 매칭 → Elasticsearch 검색 → 필요한 경우 LLM 판단 → 사용자 검토** 순서로 설계.
3. **실제 외부 발주·결제는 제외**, 내부 PO 및 발주 금액·연락처 확인·수동 GR 유지.
4. **다단계 결재·송장 검증은 이번 일정 제외**, P2 확장 후보로만 기록.
5. **MES 전체 제외**, BOM/간소화 MRP는 P2 확장 후보.
6. **B가 공통 인증·사용자·권한 인프라 담당**, **A가 공통 UI/UX 디자인 담당**.
7. **CI/CD, 배포 인프라, 공통 로깅·모니터링, PostgreSQL 공통 운영·백업은 두 사람 공동 작업**.

8. **D-01:** 하나의 PR에서 여러 PO로 분할 발주한다. 동일 PR 품목의 유효 PO 발주 합계는 승인 수량을 넘지 않는다. PO당 공급업체 1곳.
9. **D-02:** PR 헤더 전체 일괄 승인·반려만 수행한다. 품목별 부분 승인 제외.
10. **D-03~11:** 품목별 기준단위+Decimal 수량(환산 없음, KRW), 개시 재고 원장, PO 잠금+요청 멱등성, 사용자 입력 재고 임계값, 제한된 XLSX/텍스트 PDF, 버전 있는 구매 규정 1종, 세션 인증 우선, Rust·모델은 PoC 후 결정, DB 커밋 이후 ES 색인·실패 재처리, 핵심 계약부터 점진적 명세화.

### 아직 설계·검증이 필요한 사항

Rust AI 서비스/프레임워크 채택, Java·Spring Boot 세부 버전, LLM·Embedding 모델, 세션 인증 상세(CSRF/서비스 간 신원 전달)·세부 권한, 상세 PR/PO/GR 상태와 취소 정책, NUMERIC 정밀도·반올림, 색인 재처리 구현, API/ERD, 실제 배포 플랫폼·예산, UI 세부 디자인. **담당자 확정과 세부 구현 방식 확정은 별개**다.

## 14. 최종 산출물

구매·재고 ERP 웹, 통합 AI Assistant(대화형 ERP Agent + 파일 분석·품목 매칭), PostgreSQL·Elasticsearch 기반 업무 데이터, 핵심 자동화 테스트와 AI 평가 결과, 작동하는 배포·시연 환경, PRD·기능·화면·ERD·OpenAPI·AI·운영 명세.
